# yaLIBCFG - постановка задачи и проект

Состояние (22-NOV-2026): этап 1 (разбор, дерево, пути, запись без потерь) и сравнение (этап 3,
по просьбе владельца - раньше схемы) сделаны: листинг в духе DIFFERENCES, отпечаток - UUID v5 из
настроек.  Следующий - схема.

## 1. Зачем

Библиотека на C для конфигурационных файлов в виде дерева, с синтаксисом, совместимым с
libconfig.  Сделана для программ, которые хранят свою конфигурацию декларативно: файл описывает
желаемое состояние, программа сравнивает его с текущим и применяет разницу.

Чем отличается от libconfig - то, ради чего ее стоит писать:

| | libconfig | yaLIBCFG |
|---|---|---|
| Комментарии и форматирование при записи | теряются | **сохраняются**: файл без правок записывается байт в байт; правится только измененное |
| Проверка значений | нет, только типы | **схема**: тип, диапазон, ключевые слова, обязательность, ключ списка |
| Сравнение двух деревьев | нет | **diff**: список "добавить / изменить / удалить" с путями |
| Ошибки | строка, текст | условия VMS (`%CFG-E-RANGE, ...`) с файлом, строкой и столбцом |
| Списки групп (порты, правила) | только по позиции | **по ключу** (id, name) из схемы: перестановка в файле - не изменение |
| Стиль, сообщения | свой | StarLet: статусы по младшему биту, $PUTMSG_FAO, ASC |
| Лицензия | LGPL-2.1 | Apache-2.0 |

Не цели: замена JSON/YAML, сериализация произвольных данных, потоковый разбор гигабайтных файлов.

## 2. Синтаксис

Совместим с libconfig 1.7: любой корректный файл libconfig разбирается в то же дерево.

    файл      := { параметр }
    параметр  := имя ( "=" | ":" ) значение [ ";" | "," ]
    значение  := скаляр | массив | список | группа
    массив    := "[" [ скаляр { "," скаляр } ] "]"          - скаляры одного типа
    список    := "(" [ значение { "," значение } ] ")"     - что угодно
    группа    := "{" { параметр } "}"
    скаляр    := целое | целое64 | дробное | логическое | строка
    имя       := [A-Za-z*] [-A-Za-z0-9_*]*

- целое: десятичное, 0x 16-ричное, 0b двоичное, 0o восьмеричное (как в libconfig 1.7; ведущий 0
  без o - просто десятичное: 0027 = 27); суффикс L или LL - 64 бита; без суффикса десятичное, не
  влезающее в 32 бита, становится 64-битным (libconfig 1.5 молча обрезал его до 32 бит);
  0x/0b/0o без суффикса до 0xFFFFFFFF - 32-битное с переносом знака (0xFFFFFFFF = -1), как в libconfig.
- дробное: 1.5, 1e-3, .5.  логическое: true/false в любом регистре.
- строка: "..." с \" \\ \n \t \r \f \xHH; соседние строки склеиваются ("ab" "cd").
- комментарии: # ..., // ..., /* ... */.
- `@include "файл"` - путь относительно включающего файла; глубина ограничена, циклы - ошибка.
  Включаемый файл должен состоять из целых параметров (libconfig вклеивает его как текст и
  терпит половину группы - мы нет).  Директива стоит там, где может стоять параметр.
- запятая перед закрывающей скобкой (`[1, 2,]`) - ошибка, как в libconfig: что пишем, то и читаем.
- массив: целые 32 и 64 бита считаются одним типом.
- разбор останавливается на первой ошибке.

Расширения сверх libconfig - не вводим в первой версии.  Кандидаты на потом, только по
необходимости: числа с единицами (10G, 1500ms) - пока это строки, единицы разбирает схема.

## 3. Модель данных

Дерево узлов.  Узел:

- имя (у элементов массива и списка - нет), тип, значение;
- дети (у группы, списка, массива) в порядке файла;
- **позиция в источнике**: файл, строка, столбец - для сообщений;
- **отрезки исходного текста**: сам узел, ведущие комментарии и пустые строки, хвостовой
  комментарий на той же строке - для записи без потерь;
- флаг "изменен" - узел, созданный или правленный программой.

Память: арена на дерево; освобождается целиком.  Строки внутри - указатель + длина (значения
бывают длиннее 255, ASC для них не годится); имена - ASC.

## 4. Запись без потерь

- Неизмененный узел пишется его исходным отрезком текста как есть.
- Измененный значением - заменяется только текст значения, комментарии вокруг остаются.
- Новый узел - канонически: отступ соседей, `имя = значение;`.
- Удаленный - исчезает вместе с ведущими комментариями (они его описывали).
- Гарантия, проверяемая тестами: разбор + запись без правок = байт в байт.
- Включенные файлы пишутся каждый в свой файл; `@include` остается.

## 5. Пути

`ports.[1].mtu`, `vlans.[id=100].name`:

- `.` - шаг в группу, `[n]` - элемент списка/массива по позиции (как в libconfig);
- `[ключ=значение]` - элемент списка групп по ключу (расширение; ключ - из схемы или явный).

На пути держится связь с командами DCL: `SET PORT 1 /MTU=9216` -> `ports.[id=1].mtu = 9216`.

## 6. Схема

Таблица на C, в духе CLI_PQDESC из cli_routines:

- имя, тип (INT, INT64, FLOAT, BOOL, STRING, KWD, IPV4, IPV6, MAC, GROUP, LIST, ARRAY);
- флаги: REQUIRED, KEY (поле-ключ элементов списка), UNIQUE, DEPRECATED;
- диапазон (min/max), таблица ключевых слов (как CLI_KEYWORD), значение по умолчанию;
- для GROUP/LIST - схема детей; для LIST - имя поля-ключа;
- необязательная рутина проверки (связи между полями).

Проверка (`CFG$VALIDATE`) собирает все ошибки, а не останавливается на первой, каждая -
условие с позицией: `%CFG-E-RANGE, mtu = 99999 out of range 64..9216, STARTUP.CFG line 12`.
Неизвестный параметр - ошибка (опечатки не проходят молча); можно разрешить флагом.

## 7. Сравнение

`CFG$DIFF(старое, новое)` - список изменений {ADD | DEL | MOD, путь, узел старый, узел новый}:

- списки групп со схемным ключом сравниваются по ключу, без схемы - по позиции;
- порядок: удаления - от листьев к корню, добавления - от корня к листьям;
- на этом программа строит COMMIT (применить разницу через обработчики по узлам схемы) и
  ROLLBACK (применить обратную разницу).

## 8. Программный интерфейс (наброски)

Все рутины возвращают статус условия VMS (успех - младший бит), результаты - через выходные
параметры.

    CFG$PARSE_FILE    (path, opts, &tree)
    CFG$PARSE_STRING  (buf, len, name, opts, &tree)
    CFG$WRITE_FILE    (tree, path)            CFG$WRITE_BUF (tree, &buf, &len)
    CFG$FREE          (tree)
    CFG$LOOKUP        (tree | node, path, &node)
    CFG$GET_INT / _INT64 / _FLOAT / _BOOL / _STRING  (node, path, &value)
    CFG$SET_INT / ... (node, path, value)     - создает недостающее по пути
    CFG$ADD           (parent, name, type, &node)
    CFG$DELETE        (node)
    CFG$FOREACH       (node, rtn, arg)
    CFG$VALIDATE      (tree, schema, &errlist)
    CFG$DIFF          (old, new, schema, &difflist)
    CFG$NODE_INFO     (node, &name, &type, &file, &line)

Потокобезопасность: дерево - одного потока; разные деревья независимы.

## 9. Сообщения

Facility CFG, номер 0x0114 (utility_routines/doc/FACILITIES.txt, взят 22-NOV-2026).
Предварительно: SYNTAX, UNTERM (незакрытая строка/комментарий/скобка), BADNUM, BADESC,
DUPNAME, INCLUDE (не открыть), INCDEPTH, INCLOOP, NOTFOUND, TYPE, RANGE, BADKWD, REQUIRED,
UNKNOWN, DUPKEY, NOKEY, NOMEM, WRITE.

## 10. Состав проекта

    include/yalibcfg.h      - интерфейс
    include/yalibcfgdef.h   - коды условий, константы
    src/cfg_lex.c        - лексер с отрезками текста и позициями
    src/cfg_parse.c      - разбор в дерево, @include
    src/cfg_tree.c       - узлы, пути, get/set/add/delete
    src/cfg_write.c      - запись без потерь
    src/cfg_schema.c     - проверка
    src/cfg_diff.c       - сравнение
    src/cfgtool.c        - утилита CFGTOOL: CHECK, FORMAT, DIFF, GET, SET (на cli_routines)
    test/                - корпус файлов libconfig, тесты "байт в байт", схемы, diff; фаззинг
    doc/                 - руководство на русском и английском, справка HELP

Сборка - CMake, библиотека статическая (как libstarlet.a) и пакет Debian libyalibcfg-dev через
CPack, как у StarLet.  Зависит от StarLet.

## 11. Этапы

1. Лексер + разбор + дерево + пути + запись без потерь; тесты байт в байт на корпусе libconfig.
2. Схема и проверка; CFGTOOL CHECK/FORMAT/GET/SET.
3. Diff по ключам; CFGTOOL DIFF.
4. Руководство, справка, пакет, выпуск.

## 12. Решения (22-NOV-2026)

- Имена хранятся как написаны; поиск без учета регистра - флагом при разборе.
- На выходе всегда синтаксис, совместимый с libconfig; путь `[ключ=значение]` - только в API.
- Фаззинг (libFuzzer) - после выпуска 1.
